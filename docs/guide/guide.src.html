Start here

ai-agent-lib gives every LangGraph agent and MCP server the same governed plumbing: who the caller is, what they may do, a record of what happened, content checks, a model chosen by configuration, and data reached only through named queries. Teams write the graph and the tools. The library hands back ordinary LangGraph and LangChain objects that happen to be governed.

Ten minutes from an empty folder to a tested agent and MCP server, with no cloud account. <lib> is your checkout of the repository.

uv run --project <lib> --package ai-agent-lib-cli agentlib init payments-ai --owner payments
cd payments-ai
uv sync --all-packages
uv run agentlib new mcp directory --description "The people directory"
uv run agentlib new agent helper --description "Answers questions about people" --mcp directory
uv sync --all-packages
uv run pytest                      # the generated tests, offline
uv run agentlib check              # the whole gate CI runs
uv run agentlib doctor             # checks every service against its .env
uv run agentlib run directory      # terminal 1: the MCP server
uv run helper "Who is in the payments team?"   # terminal 2: the agent

Then read on in this order: the core idea for the mental model, the worked example for the code you just generated, configuration to switch adapters, and the testing, observability and evals chapters before you go to production. When something fails, when something goes wrong explains the error you are reading. The reference lists every variable, option and flag with its default.

The core idea spec §1–2

An agent's business logic is small. What makes it hard to ship in an enterprise is the ring of concerns around every model call and every tool call: identity, authorisation, audit, content safety, data access rules, observability, configuration per environment. Each team used to solve these again, differently. ai-agent-lib solves them once, behind interfaces, and lets each environment choose how.

Five promises

  • Native LangGraph. No graph DSL. You write StateGraph code; five calls into the library make it governed.
  • One code path from laptop to Fargate. Environment variables choose an adapter for each concern. Local and server-side adapters mix freely, so you can run the real Bedrock model against local files and rules.
  • Testable by injection. Every dependency is injected. Unit tests need no network, no cloud account and no wall-clock time.
  • Fail closed. A policy, audit or guardrail failure stops the request. Nothing quietly degrades to a fallback.
  • AWS first, portable later. Other clouds arrive as separate packages that pass the same contract tests.

What the library does not do

  • It is not an agent framework or a hosting platform. You own the graph topology, prompts and domain schemas.
  • It does not run a sign-in flow. The caller's identity provider issues tokens; the library verifies them and carries the verified identity.
  • It never loads code from configuration, and it provisions nothing itself: agentlib deploy writes Terraform that you review and apply.

Architecture and stack spec §3–7

Configuration is read once into a frozen ServiceConfig. A ServiceContainer builds one adapter per port from a trusted registry of factories, and hands your code governed LangGraph objects. Graph code never sees which adapter sits behind a port.

.env + environment→ConfigResolver→ServiceConfig→ServiceProviders→ServiceContainer→your graph / MCP server

How a call is governed spec §8

Every model call and every tool call passes through a pipeline of interceptors. The order is fixed by an enum, so no option can put policy after the call or skip the audit. Solid boxes run today; dashed boxes are reserved positions for stages that are specified but not built yet.

Model pipeline

audit→deadline→budget→identity→policy→context→input guardrails→structured output→output guardrails→resilience→model

Tool pipeline

audit→deadline→budget→registry→policy→approval→input guardrails→idempotency→judge→framing→result guardrails→resilience→tool
  • Audit is outermost, so it records denials and failures from every stage inside it. If the record cannot be written the call fails with IntegrityError, even if the call itself succeeded.
  • Deadline bounds the whole call, every check included, by the caller's deadline. An answer that arrives after it, even from a step that blocked the event loop, is refused (PolicyDenied, reason deadline_exceeded) and audited, never returned.
  • Identity requires a RequestContext and refuses a caller past their deadline (PolicyDenied, reason deadline_exceeded).
  • Policy asks the policy decision point about model.route (the model alias) or tool.call. The rule that allowed it is written to the audit record as policy_reason_code.
  • Registry refuses a tool that is not registered for the agent, or whose live input schema no longer matches its pin.
  • Guardrails check prompts, replies, tool arguments and tool results for size and personal data, and tool results for prompt-injection markers. Each finding is flag (record it) or block (deny).
  • Framing wraps every tool result as untrusted data before the model sees it, which blunts injected instructions.
  • Structured output validates the reply against a schema inside the pipeline, so a malformed reply fails and is audited as failed.
  • Budget counts model calls, tool calls and tokens per request and stops a request that reaches its limit with BudgetExceeded, before the call is made. The count is kept per caller and per invocation: a request ID a caller sends correlates records but never shares a budget with another caller or another request.
  • Resilience sits next to the model or the tool: it gives each attempt a deadline and tries a transient failure again with growing, jittered waits, within the caller's deadline. No attempt outlasts that deadline: when it runs out the call is denied with deadline_exceeded, and no retry starts that the deadline leaves no time for. A tool is tried again only when it only reads. The audit record says how many attempts there were.

On an MCP server the same idea applies at the door: services.mcp_server_kwargs() installs middleware that verifies the token, checks the caller's agent against the registry, asks policy about tool.call, and applies data.query obligations such as masked columns and row limits to every query result.

Configuration spec §5

Configuration is environment variables with the EAP_ prefix. Locally they come from the service's .env file; deployed, from the task definition. Your code never reads a variable: it receives a typed, frozen ServiceConfig.

How a value is resolved

  1. ServiceContainer.from_env() reads the process environment first, then .env. The environment wins, so a deployment or a shell can override any line of the file.
  2. An EAP_ variable the library does not know stops startup, with a suggestion: EAP_MODEL_PROVIDR (did you mean EAP_MODEL_PROVIDER?).
  3. EAP_PROFILE supplies a default adapter for every section. EAP_<SECTION>_PROVIDER overrides one section; EAP_<SECTION>_OPTIONS passes that adapter's options as JSON.
  4. Options are validated by the adapter's own Pydantic model. Unknown keys and wrong types stop startup.
  5. Relative paths in options resolve against the folder of the .env file, so a service runs the same from any working directory.
  6. The one-way guard runs last: outside local, a local-only adapter is refused, and inside ECS, Fargate or Lambda the deployment environment must be named.

Every adapter declares its options model, so all of them are checked before anything is built and every problem is reported at once. To see what an adapter takes, with types, defaults and meanings, ask the command line; --schema prints JSON Schema for an editor:

uv run agentlib config options                  # every port and its adapters
uv run agentlib config options audit firehose   # one adapter's options
uv run agentlib config options limits           # EAP_LIMITS: timeouts, retries, budgets

To see the result and where each value came from, with secrets masked:

Rule of thumb. Put structure in files (rules, registries, named queries) and environment-specific facts in variables (where the stream is, which tenant). The same rules file then runs in the local engine and in OPA, and the same SQL runs on DuckDB and Redshift.

Worked example: a people-directory agent

We build what Start here generated: an MCP server, directory, with a tool over a CSV of people, and an agent, helper, that calls it. Analysts may see names and teams but not email addresses; managers see everything. Every file shown is what agentlib writes today, trimmed only of comments.

  1. The workspace

    uv run --project <lib> --package ai-agent-lib-cli agentlib init payments-ai --owner payments
cd payments-ai && uv sync --all-packages

    A workspace holds every agent and MCP server of one team, with one registry/ (which agents and tools exist), one policies/agentlib/rules/data.yaml (who may do what) and one uv environment. agentlib.toml records the answers it was generated from, so agentlib init --answers agentlib.toml recreates it elsewhere.

  2. The MCP server: two touchpoints

    uv run agentlib new mcp directory --description "The people directory"
# or start from your own data:
#   --from-csv ./exports   --from-openapi ./api.yaml   --from-redshift sales --database dw
    # mcp-servers/directory/src/directory/server.py
def build_server(services: ServiceContainer) -> MCPServer[Any]:
    server: MCPServer[Any] = MCPServer(
        APPLICATION,
        instructions=INSTRUCTIONS,
        **services.mcp_server_kwargs(SERVER_ID, application=APPLICATION),  # touchpoint 1
    )
    source = services.data_source(DATA_SOURCE)                             # touchpoint 2

    @server.tool(name="directory.people_by_team")
    async def people_by_team(team: str) -> dict[str, Any]:
        """The people in one team: platform, payments or risk."""
        result = await source.query("people_by_team", {"team": team})
        return result.to_payload()

    return server

    Touchpoint 1 installs the governing middleware: token check, registry check, policy and audit for every tool call. Touchpoint 2 returns a data source by name; the tool runs a named query, never SQL from a caller. The query is a file with its contract in the header:

    -- queries/people_by_team.sql
-- description: The people in one team: platform, payments or risk.
-- param team: string
-- max_rows: 50
-- classification: confidential
SELECT person_id, name, team, email
FROM people
WHERE team = :team
ORDER BY person_id
    # mcp-servers/directory/.env
EAP_DATA_SOURCES={"people": {"kind": "duckdb_csv", "data_dir": "data", "queries_dir": "queries"}}
EAP_CHECKPOINT_PROVIDER=none
EAP_REGISTRY_OPTIONS={"agents_path": "../../registry/agents.yaml", "tools_path": "../../registry/mcp-tools.yaml"}
EAP_POLICY_OPTIONS={"path": "../../policies/agentlib/rules/data.yaml"}
EAP_IDENTITY_OPTIONS={"audience": "directory", "subject": "dev-user", "tenant": "dev-tenant", "roles": ["analyst"]}

    In production only the data source line changes: {"people": {"kind": "redshift_data", "queries_dir": "queries", "database": "dw", "workgroup": "analytics"}}. The SQL is the same file.

  3. The agent: five touchpoints

    uv run agentlib new agent helper --description "Answers questions about people" --mcp directory
    # agents/helper/src/helper/graph.py
async def registered_mcp_tools(services: ServiceContainer) -> list[BaseTool]:
    entry = services.registry.agents.get(APPLICATION)
    tools: list[BaseTool] = []
    for server in entry.mcp_servers if entry is not None else ():
        tools += await services.mcp_tools(server)                    # touchpoint 2
    return tools


def build_graph(services: ServiceContainer, mcp_tools: Sequence[BaseTool] = ()) -> CompiledStateGraph:
    tools = services.tools([greet], read_only=["greet"])             # touchpoint 1
    tools += mcp_tools
    model = services.model("default").bind_tools(tools)              # touchpoint 3

    async def agent(state: State) -> dict[str, list[AnyMessage]]:
        reply = await model.ainvoke([SystemMessage(SYSTEM_PROMPT), *state["messages"]])
        return {"messages": [reply]}

    builder = StateGraph(State, context_schema=RequestContext)
    builder.add_node("agent", agent)
    builder.add_node("tools", ToolNode(tools))
    builder.add_edge(START, "agent")
    builder.add_conditional_edges("agent", tools_condition)
    builder.add_edge("tools", "agent")
    return builder.compile(**services.compile_kwargs())              # touchpoint 4


async def answer(graph, services, context: RequestContext, question: str) -> str:
    result = await graph.ainvoke(
        {"messages": [HumanMessage(question)]},
        **services.invocation(context),                              # touchpoint 5
    )
    return str(result["messages"][-1].content)
    TouchpointWhat it adds
    1 services.tools()Your own functions as tools, each call through the tool pipeline: policy, guardrails, framing, audit.
    2 services.mcp_tools()The tools of a registered server, with a token exchanged for that server per call and pins checked.
    3 services.model()The model behind an alias, through the model pipeline. bind_tools and with_structured_output work as in LangChain.
    4 services.compile_kwargs()The configured checkpointer, with thread IDs scoped to the caller. A thread is read or written only for the caller the run's context names; outside a run, bind one with bind_request_context(context) before aget_state.
    5 services.invocation(context)The caller's RequestContext for this run, which every stage reads.

  4. Rules and registry

    Each new command appends the rules its service needs. The file is yours; agentlib never changes or removes a rule that is there. The first matching rule allows; no match denies. A document that breaks the schema (an unknown key, action or obligation, a duplicate id) denies every call with invalid_rules, rather than letting part of it through.

    # policies/agentlib/rules/data.yaml (excerpt)
schema: agentlib.rules/v1
rules:
  - id: directory-analysts-see-no-email
    actions: [data.query]
    applications: [directory]
    roles: [analyst]
    resources: ["people.*"]
    max_classification: confidential
    obligations:
      mask_columns: [email]
      max_rows: 50

  - id: helper-uses-its-models
    actions: [model.route]
    applications: [helper]
    resources: [default]

  - id: helper-calls-directory
    actions: [tool.call]
    applications: [helper]
    resources: ["directory/*"]
    max_classification: confidential

    The registry lists the server and pins each tool's input schema. After you change a tool's arguments on purpose, pin again; a change by accident fails the tests and the deployed agent refuses the tool.

    uv run agentlib registry pin directory
uv run agentlib policy test            # decides tests/policy-samples.yaml
uv run agentlib policy test --opa      # and checks that OPA agrees

  5. Tests, written before the change

    Three layers come generated: the agent with fakes, the agent with its own configuration, and the two services together in one process. Here is the last, which proves the masking rule end to end with no network:

    # tests/test_helper_with_directory.py (excerpt)
async def ask_as(roles, tmp_path, question, *replies) -> str:
    server_config = load_test_config(SERVER_ENV, state_dir=tmp_path / "server")
    agent_config = load_test_config(AGENT_ENV, state_dir=tmp_path / "agent", roles=roles)
    async with ServiceContainer(server_config) as server_services:
        connector = InProcessMcpConnector({SERVER_ID: build_server(server_services)})
        async with ServiceContainer(
            agent_config, scripted_providers(*replies), mcp_connector=connector
        ) as services:
            context = await services.authenticate(None, application=AGENT, thread_id="th-1")
            graph = build_graph(services, await services.mcp_tools(SERVER_ID))
            await answer(graph, services, context, question)
            return last_shown_to_model(services)


async def test_an_analyst_sees_no_email(tmp_path: Path) -> None:

When something goes wrong

Every error the library raises says three things: what the code expected, what it got instead, and how to fix it. The entry points a generated service has print it like this, with the line in the library that raised it and the line of your code that led there:

helper: ConfigurationError: the options of provider 'jsonl' are not valid (2 problems)
  expected: path: a path, written as text; only known options: fsync, path, tracing
  got: path = 5; an unknown option 'fsynk' (did you mean 'fsync'?)
  fix: correct the options; the developer guide lists every option with its default
  note: while building the audit adapter 'jsonl', chosen by EAP_AUDIT_PROVIDER with options from EAP_AUDIT_OPTIONS
  raised at: .../ai_agent_lib_core/contracts/options.py:279 in parse_options
  your code: agents/helper/src/helper/__main__.py:21 in _run

Anatomy of an error

PartWhere it comes fromIn code
MessageOne line: what failederror.summary
expected / got / fixSet by the code that raised iterror.expected, error.actual, error.fix, error.facts()
reasonFor a PolicyDenied: the reason code, and the rules that came closest and what each needederror.reason_code
noteContext added on the way up: which adapter, which variable chose it, how many attemptserror.__notes__
caused byThe error underneath, shortened and redactedcauses(error)
raised at / your codeThe traceback: the library's frame and the deepest frame outside the libraryexplain(error)

Raise the same kind of error from your own code: the facts are keyword arguments, and str(error) shows them.

raise ValidationFailed(
    "the input is not a question",
    expected='an object such as {"question": "Say hello to Ada."}',
    actual="no non-empty 'question' in it",
)

In the logs

A logged error becomes fields, so a log search finds every error of one kind and every error whose fix is the same: error_type, error_at, error, error_reason, error_expected, error_actual, error_fix, error_notes, error_causes and error_in_your_code. The HTTP entry points log a refused or failed request with these fields and answer the caller with a code only ({"error": "denied", "reason": "no_matching_rule"}), never the message.

What is never shown

  • Secrets and tokens. Anything shaped like a credential, including a password in a URL, is replaced with [redacted] in messages, logs and output.
  • Caller content. A prompt, a tool argument or a query parameter never enters a message. When it helps to debug, the code puts it in error.detail, which is not part of str(error) and is logged only where shows_details(config) is true: on a developer's machine.
  • A backend's own error text from a database or a cloud API is kept in detail too; the message names its type.

Practices

  • Let entry points report. Generated __main__ and service modules end in return report_error(program, error, details=shows_details(config)): one clear block and exit code 1, with a full traceback for an error that is not the library's.
  • Read the note line first when the message is about an adapter: it names the variable that chose the adapter and the one that holds its options.
  • For a denial, the closest rules are named with what each needed; reproduce it with a sample in tests/policy-samples.yaml and agentlib policy test.
  • A retried call carries the note tried N times, the last error is shown; its audit record has attempts.

Scripting the model

A scripted model replays replies in order. A string is a plain answer; calls_tool(name, **arguments) is the model deciding to call a tool, and structured_reply(Schema, **values) is a structured answer. Name the tool as you registered it, directory.people_by_team or greet: the helper spells it the way the model API sees it.

async def test_the_agent_calls_its_tool_and_answers() -> None:
    fakes = Fakes(model=FakeChatModelProvider([calls_tool("greet", name="Ada"), "I said hello to Ada."]))
    async with fakes.container() as services:
        reply = await ask(services, context(), "Say hello to Ada.")

    assert reply == "I said hello to Ada."
    prompts = fakes.model.models[0].calls
    assert prompts[1][-1].content == frame_untrusted("greet", "Hello, Ada!")
    assert [r.event for r in fakes.audit.records] == ["model.call", "tool.call", "model.call"]

Practices that pay off

  • Test the rules through the agent. The as-configured layer reads .env.example, so a missing rule fails a test, not a demo. Assert on policy_reason_code in audit_records() to prove which rule allowed each step.
  • Test denials as much as successes. Pass roles=[...] to load_test_config or call_tool_as and check the refusal and the masked columns.
  • Never call a real model in unit tests. load_test_config selects the fake model unless you pass fake_model=False. Real-model runs are evals.
  • The network is blocked. Generated workspaces run tests with pytest-socket, allowing only this machine, so an accidental call fails loudly. An eval opts back in with @pytest.mark.enable_socket.
  • Run the gate before you push. agentlib check runs what the generated CI workflow runs (ruff, the format check, mypy, pytest and policy test; add --opa to compare with OPA), and names the step that failed.
  • Pin time and IDs. Use FrozenClock and SequentialIds when an assertion depends on them.
  • Keep the generated tests. They encode the library's contract for your service. agentlib update refreshes them when the library changes.

Structured output for deterministic tests spec §10

Free text is hard to assert on and hard to consume downstream. When a model's answer feeds code (a routing decision, a classification, an extraction), ask for a typed reply. with_structured_output accepts a Pydantic model, a JSON Schema or a StructuredOutput. The model is asked to answer by calling one tool whose parameters are the schema (tool_choice="any"), and the reply is validated inside the model pipeline. A reply that does not match raises ValidationFailed and is audited as failed, so bad output never reaches your code silently.

class Triage(BaseModel):
    """How to route one customer message."""
    category: Literal["billing", "fraud", "other"]
    urgent: bool
    reason: str = Field(max_length=200)


async def triage(services: ServiceContainer, context: RequestContext, text: str) -> Triage:
    model = services.model().with_structured_output(Triage)
    with bind_request_context(context):   # inside a graph node, invocation(context) does this
        return await model.ainvoke(
            [SystemMessage("Classify the customer's message."), HumanMessage(text)]
        )

Tests script the answer with structured_reply: pass an instance of the schema, or the schema and the values, including values the schema would refuse. It names the reply the way the model API sees the schema ({"title": "Account answer"} is offered as Account_answer), so a test never has to.

async def test_a_valid_reply_becomes_a_typed_value() -> None:
    fakes = Fakes(model=FakeChatModelProvider(
        [structured_reply(Triage(category="fraud", urgent=True, reason="card used abroad"))]))
    async with fakes.container() as services:
        result = await triage(services, CALLER, "Someone used my card in Lisbon!")
    assert result == Triage(category="fraud", urgent=True, reason="card used abroad")


async def test_a_reply_outside_the_schema_fails_the_call() -> None:
    fakes = Fakes(model=FakeChatModelProvider([structured_reply(Triage, category="refund", urgent="yes")]))
    async with fakes.container() as services:
        with pytest.raises(ValidationFailed):
            await triage(services, CALLER, "Where is my refund?")
    assert [r.outcome.value for r in fakes.audit.records] == ["failed"]
  • Keep schemas small and closed: Literal for categories, bounds on strings and numbers. The schema is the contract between the model and your code.
  • Put routing decisions in structured nodes and keep free text for the final answer to the person. Graph edges then branch on typed values that tests control exactly.
  • The same schema becomes your eval scorer: an exact match on category is a metric, as the next chapters show.
  • Use include_raw=True when you also need the raw message, for example to log token usage.

Operational signals (logs, traces, metrics) answer "is the service healthy and fast" for the people who run it. Neither ever holds prompts, replies, tool arguments, query parameters or tokens.

Every log line also carries time, level, logger, message and service, and inside a request request_id and application. Anything shaped like a credential is replaced with [redacted]; other libraries' loggers are quiet below WARNING. The library's own lines carry metadata only; a message or field your code logs is written as you wrote it, so keep caller content out of it. An error is logged with its facts as fields (error_expected, error_actual, error_fix and the rest; see when something goes wrong). Spans record an error's type, never its message: the request spans do not attach the exception, so no caller content reaches the trace.

Set it up in a service

from ai_agent_lib_core.observability import configure_logging, start_telemetry

def main() -> int:
    configure_logging(APPLICATION)                          # first: JSON lines on stdout
    stop_telemetry = start_telemetry(APPLICATION, config)   # OTLP to the collector when EAP_TELEMETRY is on
    try:
        asyncio.run(_serve(host, port))
    finally:
        stop_telemetry()                                    # flush the last spans and metrics
# the service's environment
EAP_TELEMETRY=opentelemetry                             # spans per call, events and metrics
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318      # the sidecar collector
OTEL_RESOURCE_ATTRIBUTES=deployment.environment=prod,service.version=1.4.0

Generated services already do this. start_telemetry does nothing when the settings leave telemetry off, and calls configure_telemetry when they turn it on, which needs the otel extra (generated services depend on it). The service name you pass becomes service.name and wins over OTEL_SERVICE_NAME; every other exporter setting is a standard OTEL_ variable read by the SDK. In tests pass span_exporter=InMemorySpanExporter() and a metric_reader to assert on spans without a collector.

Practices

  • Correlate by request_id. The agent sends it to MCP servers with each call, and it appears in the agent's and the server's audit records, log lines and spans. Send x-request-id from your caller to join the chain from the edge.
  • Turn telemetry on in dev and prod with EAP_TELEMETRY=opentelemetry. It is off by default so unit tests stay silent. (The older audit option tracing still turns it on.) In tests, RecordingTelemetry records spans so you can assert on them.
  • Alert on outcomes, not on text. Useful first alerts: agentlib.events{outcome="denied"} rising (a rules change or an attack), outcome="failed" on model.call (structured output or provider errors), agentlib.duration p95 per model_alias.
  • Cost. Model audit records carry input_tokens and output_tokens with tenant, subject and application; aggregate them from the audit stream for cost attribution.
  • Keep content out. If you need prompts and replies for debugging or evals, store them deliberately, classified and with retention, in a store you own. Do not add them to log lines or span attributes.

One trace from the edge to the data. The agent's MCP client puts the W3C traceparent of the current span in each call's metadata, and the server continues that trace, so a backend shows the request, its model and tool calls, the MCP call and the server's query as one tree. Span names and attributes follow the OpenTelemetry GenAI semantic conventions.

Evals, offline and online spec concern 10

Unit tests prove the plumbing with a scripted model. Evals measure the behaviour of the real model on your task. ai_agent_lib_core.evaluation holds the pieces, off the request path (an import rule keeps it there), and every generated agent comes with an eval ready to run.

Offline: a dataset, a scorer, a bar

Cases are JSON lines next to the service: an id, the input, what a good answer has in expected, and optional tags. Lines starting with # are comments.

# agents/support/evals/triage.jsonl
{"id": "card-abroad", "input": {"text": "Someone used my card in Lisbon, I'm in Leeds!"}, "expected": {"category": "fraud", "urgent": true}}
{"id": "double-charge", "input": {"text": "Why was I charged twice for March?"}, "expected": {"category": "billing", "urgent": false}, "tags": ["billing"]}

Score with the same structured schema the code uses, so most metrics are exact matches rather than opinions:

from ai_agent_lib_core.evaluation import exact, judged, load_cases, run_eval, scored_by
from ai_agent_lib_core.testing import load_eval_config


@pytest.mark.eval
@pytest.mark.enable_socket                                  # the network is blocked for other tests
async def test_triage_meets_its_bar(tmp_path: Path) -> None:
    config = load_eval_config(SERVICE / ".env", state_dir=tmp_path)   # keeps the real model
    if config.model.provider == "fake":
        pytest.skip("set a real model in .env to run evals")
    async with ServiceContainer(config) as services:
        context = await services.authenticate(None, application=APPLICATION, thread_id="eval")
        report = await run_eval(
            lambda case: triage(services, context, case.input["text"]),
            load_cases(SERVICE / "evals" / "triage.jsonl"),
            [exact("category"), exact("urgent")],
            concurrency=4,
        )
    print("\n".join(report.summary()))
    report.require({"category": 0.90, "urgent": 0.85})

report.require fails with the metric, the bar and the score (expected: category >= 0.90, then the score it got) and names the cases below it. report.by_tag breaks the scores down by tag, and report.to_json() is the record to keep with the change.

uv run agentlib eval support      # before merging a prompt, model or rule change
uv run agentlib eval              # every service
  • Gate changes on evals. Run them when a prompt, model alias, tool description or rule changes, and keep the report with the commit.
  • Test the scorer itself with a scripted model, so a broken scorer cannot pass silently: run_eval runs unchanged on Fakes.
  • Use a judge only for what cannot be matched. For tone or faithfulness, add a judge alias in EAP_MODEL_ALIASES and score with judged(services.model("judge").with_structured_output(Verdict).ainvoke, "Is the answer faithful to the sources?", name="faithful"). Calibrate the judge on a hand-labelled sample first. scored_by(name, function) takes any function of the case and the output.
  • Evals are governed calls too. They go through policy and audit, so the eval identity needs rules for model.route on the aliases it uses.

Security and governance practices spec §9, §12–13

  • Every service has its own identity. Register each agent and MCP server as an application at the identity provider. The agent's token audience is its own API; the server's audience in the registry matches the server's jwt options. Turn on accept_service_tokens only for services that are called without a user.
  • Delegate, never forward. Configure exchange on agents that call MCP servers. The server then sees the user and the agent in one token, and rules can require both (roles and agents in the same rule).
  • Write narrow rules. One application per rule, explicit resources, a max_classification. Prefer obligations (mask_columns, max_rows) to a second, broader tool. Keep tests/policy-samples.yaml covering every rule, including the denials, and run agentlib policy test --opa in CI so the two engines agree.
  • Classify data at the query. Each named query declares its classification; the registry and the agent entry declare ceilings. A request above the ceiling is refused before any data moves.
  • Treat tool results as untrusted. Framing is on by default (frame_tool_results); keep it on. Set guardrail injection and pii to block for tools that read user-generated content.
  • Pin every tool. Production servers verify their pins at startup (verify_registration(..., require_pins=True) outside local); agents refuse a tool whose schema drifted.
  • Secrets by name. Options hold secret names (auth_secret, client_secret), the secrets adapter holds values. Scope the task role to the service's Secrets Manager prefix.
  • TLS everywhere. HTTP adapters refuse plain http:// to a remote host unless allow_http is set; use ca_file for a private CA rather than turning verification off (there is no switch for that).
  • Never deploy as local. Set EAP_DEPLOYMENT_ENV in every task definition; the guard refuses development adapters there, and managed runtimes must name it.

Deployment on AWS Fargate spec §16

Each agent and each MCP server is one Fargate service. agentlib deploy derives what it needs from the settings it will run with, and writes the Terraform and the Dockerfiles; you read the plan and run terraform yourself. Nothing is applied for you and nothing calls AWS.

uv run agentlib deploy helper          # first run: writes agents/helper/deploy.env with example values
uv run agentlib deploy helper --plan   # adapters, permissions and why, sidecars, warnings
uv run agentlib deploy helper          # writes deploy/helper/ and deploy/modules/agentlib-service/

docker build -f deploy/helper/Dockerfile -t helper .
docker build -f deploy/opa/Dockerfile -t helper-opa .      # when the plan lists the OPA sidecar
cd deploy/helper && terraform init && terraform plan

Settings, not hand-written policy

deploy.env holds the EAP_ settings of the deployed service. Its values become the task's environment, so it may hold no secret: a secret variable in it stops the command, naming the variable and never its value. Settings for a developer's machine (EAP_DEPLOYMENT_ENV=local) and local-only adapters are refused too. An adapter that comes from ai-agent-lib-aws needs that distribution, with the adapter's extra (bedrock, postgres), in the service's own dependencies; telemetry needs the core otel extra. The plan names each requirement to add.

Each adapter declares, from its own options, the IAM actions it calls and the resources it calls them on. The plan lists them with the reason for each, and permissions.tf holds exactly those statements. Where a resource cannot be narrowed from the settings, such as an ID AWS assigns, the plan and the file carry a check: line. For the starting deploy.env of an agent and one Redshift data source, the adapters ask for:

{region} and {account} become the deployment's region and account in permissions.tf. An adapter of your own declares its needs with ServiceProviders.register(..., access=rule); one that does not is named in the plan, so nothing is granted silently.

Errors

Every error the library raises is an AgentLibError. Catch the type, never parse the message; read expected, actual and fix as fields (see when something goes wrong). The HTTP entry point maps them to a status and a code; the error's own text never reaches the caller.
