1. Set up and run an agent

What you are building: an agent named helper with a greeting tool and automated tests. An agent uses a language model to decide how to answer a question and whether to call a tool. A tool is a function the agent can call.

ai-agent-lib supplies the surrounding services: checking who is calling, deciding which actions are allowed, recording actions, and connecting to models and data. You write the functions and the sequence of steps the agent follows.

Before you start

  • Have Python 3.11 or newer with pip available. Check with python --version and python -m pip --version. If your machine uses py -3.11 or python3, use that command for the initial version check and virtual environment creation.
  • Get a copy of this repository and open a terminal in its top-level folder, ai-agent-lib. You should see packages/ and docs/.
  • Allow pip to reach your approved package index, or use your team's wheelhouse (a folder of pre-downloaded Python packages). The local example can run without internet access once its dependencies are installed.

A virtual environment keeps this project's Python packages separate from the system installation. The commands below use its Python executable directly, so you do not need administrator rights or permission to activate PowerShell scripts.

Create the project

Choose the instructions for your terminal. They create tutorial/ beside the library checkout. Use a different name if that folder already exists.

Windows PowerShell

Run these commands from the library checkout. Keep this terminal open.

$Library = (Get-Location).Path
python -m venv .venv
$Python = Join-Path $Library ".venv\Scripts\python.exe"
& $Python -m pip install -e ./packages/ai-agent-lib-core -e ./packages/ai-agent-lib-cli
& $Python -m ai_agent_lib_cli init tutorial --dir .. --lib-path $Library --owner learning
Set-Location ../tutorial
& $Python -m ai_agent_lib_cli new agent helper --description "A practice assistant" --model fake
& $Python -m ai_agent_lib_cli install
& $Python -m pytest
& $Python -m helper "Say hello to Ada."

$Python stores the full path to the environment's Python executable. PowerShell's & runs the command at that path.

macOS or Linux, using bash or zsh

Run these commands from the library checkout. Keep this terminal open.

LIBRARY="$PWD"
python3 -m venv .venv
PYTHON="$LIBRARY/.venv/bin/python"
"$PYTHON" -m pip install -e ./packages/ai-agent-lib-core -e ./packages/ai-agent-lib-cli
"$PYTHON" -m ai_agent_lib_cli init tutorial --dir .. --lib-path "$LIBRARY" --owner learning
cd ../tutorial
"$PYTHON" -m ai_agent_lib_cli new agent helper --description "A practice assistant" --model fake
"$PYTHON" -m ai_agent_lib_cli install
"$PYTHON" -m pytest
"$PYTHON" -m helper "Say hello to Ada."
Checkpoint: tests pass and the agent prints an answer.

The answer should be fake: Say hello to Ada. The fake model repeats your question; it does not decide to call the greeting tool. Later, a scripted test will tell the fake model exactly which tool to call.

init creates the workspace. new agent creates its source and tests. install uses the current Python's pip to install the workspace services and development tools. The --lib-path option connects this workspace to your local library checkout instead of a published library version.

Command convention for the rest of this guide: run commands from tutorial/. PowerShell examples use & $Python; on macOS/Linux, replace that prefix with "$PYTHON". In a new terminal, set the variable again to the same executable and change into tutorial/.

Optional: serve the agent over HTTP

HTTP lets another program call your agent. Start the service in your setup terminal:

& $Python -m ai_agent_lib_cli run helper

Keep it running. In a second PowerShell terminal, check readiness and send a request:

Invoke-RestMethod http://127.0.0.1:8000/readyz
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/invoke -ContentType "application/json" -Body '{"input":{"question":"Say hello to Ada."},"thread_id":"demo"}'
Send the same request with Python on macOS/Linux

Save this as try_http.py in tutorial/, then run "$PYTHON" try_http.py in a second terminal. It uses Python's standard library.

import json
from urllib.request import Request, urlopen

with urlopen("http://127.0.0.1:8000/readyz", timeout=10) as response:
    print(response.read().decode())

body = {"input": {"question": "Say hello to Ada."}, "thread_id": "demo"}
request = Request(
    "http://127.0.0.1:8000/invoke",
    data=json.dumps(body).encode(),
    headers={"Content-Type": "application/json"},
)
with urlopen(request, timeout=30) as response:
    print(json.load(response))

The response contains an output, a thread_id for the conversation, and a request_id for this call. Press Ctrl + C in the service terminal to stop it before continuing.

2. Understand the project

You now have two folders with different jobs. ai-agent-lib/ is the library's source. tutorial/ is your application workspace. Most of your work on an agent belongs in the application workspace.

tutorial/
  agents/helper/
    src/helper/
      tools.py          Functions the agent can call
      graph.py          The agent's steps and model/tool connections
      settings.py       Where this service finds its configuration
      service.py        HTTP startup and request handling
      __main__.py       The command-line question runner
    tests/              Tests of the agent and its HTTP interface
    evals/              Example questions for real-model evaluation
    .env                Local configuration; keep secrets out of Git
    .env.example        Shareable configuration template
    pyproject.toml      This service's Python dependencies
  registry/             Agent and MCP tool registrations
  policies/agentlib/rules/data.yaml
                        Which actions are allowed
  tests/policy-samples.yaml
                        Examples of allowed and denied requests
  agentlib.toml         Answers used to generate the workspace
  pyproject.toml        Shared test and development-tool settings

The words you will see in the code

Graph
A set of steps and the connections between them. LangGraph runs these steps. In this example, the graph asks the model, runs tools if requested, and asks the model again.
State
The information carried between graph steps. Here it includes the conversation's messages.
ServiceContainer
The object that creates and owns the configured services. Your code receives it as services and asks it for a model, tools, or a data source.
RequestContext
Information about one request: who is calling, the application, the request ID, and the conversation ID. A Principal represents the caller; a tenant identifies their organization or account group.
Policy
Rules deciding whether that caller and application may perform an action on a resource. For example, may helper call greet?
Adapter and provider
An adapter implements a service, such as a fake model or an AWS model. Configuration selects it by a registered provider name. This lets application code use the same interface with different implementations.
MCP
Model Context Protocol: a standard way to expose tools from a separate server. You do not need an MCP server for functions inside your agent.

Follow one request

Question→Entry point →RequestContext→ Graph→Model / tools →Answer

The entry point handles input and authentication. The graph decides which step runs next. The library applies policy, content checks, limits, and audit recording around model and tool calls. The tool function itself can stay small.

async def defines a function that may wait for other work; await waits without blocking every other request. async with ServiceContainer(...) starts services and closes them when the block ends. Ordinary tools such as greet can still be normal Python functions.

3. Add a tool, test first

Add a farewell tool that returns Goodbye, Ada!. There are three separate things to check: the function works, the graph can use it, and the policy permits it.

Step A: describe the function's behavior

Create agents/helper/tests/test_farewell.py with this complete test:

from helper.tools import farewell


def test_farewell_trims_the_name() -> None:
    assert farewell("  Ada  ") == "Goodbye, Ada!"
& $Python -m pytest agents/helper/tests/test_farewell.py

It should fail because farewell does not exist yet. This tells you the test is exercising the code you are about to add.

Step B: implement it and connect it to the graph

Append this function to agents/helper/src/helper/tools.py:

def farewell(name: str) -> str:
    """Return a goodbye for a person, given their name."""
    return f"Goodbye, {name.strip()}!"

In agents/helper/src/helper/graph.py, replace the existing tools import with:

from helper.tools import farewell, greet

Inside build_graph, replace the line that calls services.tools with the following line. Keep its indentation:

tools = services.tools([greet, farewell], read_only=["greet", "farewell"])

services.tools wraps the functions with the library's checks. read_only means these tools do not change external state, so retrying a transient failure is safe. Do not label a payment or a write operation read-only.

Run the unit test again. It should now pass.

Step C: grant the specific permission

Append this entry to the existing samples: list in tests/policy-samples.yaml, using the same indentation as its other entries:

  - name: helper says goodbye
    action: tool.call
    application: helper
    resource: farewell
    expect: allow
    reason: helper-calls-its-own-tools
& $Python -m ai_agent_lib_cli policy test

The new sample should fail: no rule permits farewell yet. In policies/agentlib/rules/data.yaml, find the existing rule with id: helper-calls-its-own-tools. Change its resources list from [greet] to [greet, farewell]. The rule should look like:

  - id: helper-calls-its-own-tools
    actions: [tool.call]
    applications: [helper]
    resources: [greet, farewell]

Run policy test again. The sample should pass. Updating an existing rule avoids introducing a duplicate rule ID or accidentally granting broader access.

Step D: prove the graph actually calls the tool

Create agents/helper/tests/test_farewell_graph.py:

from ai_agent_lib_core import Principal, RequestContext
from ai_agent_lib_core.pipeline import frame_untrusted
from ai_agent_lib_core.testing import FakeChatModelProvider, Fakes, calls_tool

from helper import APPLICATION, ask


async def test_agent_uses_farewell() -> None:
    fakes = Fakes(
        model=FakeChatModelProvider([calls_tool("farewell", name="Ada"), "I said goodbye to Ada."])
    )
    context = RequestContext(
        principal=Principal(subject="learner", tenant="tutorial"),
        application=APPLICATION,
        request_id="farewell-test",
        thread_id="conversation-1",
    )

    async with fakes.container() as services:
        reply = await ask(services, context, "Say goodbye to Ada.")

    assert reply == "I said goodbye to Ada."
    second_call = fakes.model.models[0].calls[1]
    assert second_call[-1].content == frame_untrusted("farewell", "Goodbye, Ada!")
    assert [record.event for record in fakes.audit.records] == [
        "model.call",
        "tool.call",
        "model.call",
    ]

The fake model first requests the tool, then returns a scripted answer. Checking the second model call proves the tool's result reached the model. The audit assertion checks the sequence of actions. frame_untrusted marks a tool result as data that must not be treated as new instructions.

This test uses fake permissions. It checks the graph's behavior; the policy sample in Step C checks your actual rule. Both are necessary.

& $Python -m pytest agents/helper
& $Python -m ai_agent_lib_cli policy test
& $Python -m ai_agent_lib_cli check
Checkpoint: the function, graph, and permission tests pass.

check also runs formatting, lint, and type checks. If formatting fails after pasting code, run & $Python -m ruff format . and retry. The command-line agent still echoes questions until you configure a real model.

4. Change configuration

Configuration chooses which implementations the application uses. For example, the same graph can use a fake model during tests and a real model in a deployed service. Edit the service's agents/helper/.env, then restart it.

A .env file contains NAME=value lines. Options ending in _OPTIONS are JSON objects: use double quotes around keys and strings, and keep each JSON value on one line.

EAP_PROFILE=local
EAP_DEPLOYMENT_ENV=local
EAP_MODEL_PROVIDER=fake

These lines describe the local model choice, not the whole file. Keep the generated registry, policy, and other settings already present in .env.

SettingWhat it means
EAP_PROFILEA starting set of adapter choices: local or aws. You can override individual choices.
EAP_DEPLOYMENT_ENVWhere this process actually runs. Non-local environments reject adapters intended only for local development. It is a separate setting from the profile.
EAP_MODEL_PROVIDERThe model adapter to use. fake needs no account; a real provider needs its dependencies and credentials.

Precedence: process environment variables win over the service's .env, which wins over profile defaults. Relative paths in configuration resolve from the folder containing that .env, not from your terminal.

& $Python -m ai_agent_lib_cli config explain helper
& $Python -m ai_agent_lib_cli config options model fake
& $Python -m ai_agent_lib_cli doctor helper

explain shows resolved settings and where they came from, masking secrets. options lists accepted keys and defaults. doctor tries to build and validate the configured services; with cloud adapters, this can contact those services.

Switch to a real model when you are ready

  1. Choose a provider your team supports. Look up its options with config options model anthropic or config options model bedrock.
  2. Add the dependency to agents/helper/pyproject.toml: the core anthropic extra, or ai-agent-lib-aws[bedrock]. Preserve the version constraints already used by your project.
  3. Run & $Python -m ai_agent_lib_cli install again.
  4. Set the provider, the model ID enabled for your account, and its options in the service's .env. Supply credentials using your team's approved method.
  5. Run doctor helper, then ask a question. Real model calls can incur charges.

An extra, written in brackets after a package name, installs optional dependencies. Switching a configuration value does not install them. See the dependency reference for the available groups.

5. Add an MCP server when you need shared tools

A function inside helper is enough for a tool only that agent uses. An MCP server is useful when several agents need the same tools or a separate team owns access to the data. This example adds a server named directory.

& $Python -m ai_agent_lib_cli new mcp directory --description "The people directory"
& $Python -m ai_agent_lib_cli install
& $Python -m ai_agent_lib_cli link helper directory
& $Python -m pytest
& $Python -m ai_agent_lib_cli policy test

The server includes sample CSV data, named queries, tools, and tests under mcp-servers/directory/. link adds the agent's registration, permissions, and a test connecting the two. Inspect the changed files as you would any code change.

A named query is a query you define in advance and call with parameters. The model chooses arguments; it does not receive permission to run arbitrary SQL. Data classification and policy can also restrict rows and mask columns.

After linking, keep the MCP server running when you ask the agent a question. In one terminal:

& $Python -m ai_agent_lib_cli run directory

In another terminal, with the same Python variable and workspace directory:

& $Python -m helper "Who is in the payments team?"

With the fake model, this still echoes the question. The generated connection test scripts a tool call to check the integration without needing a real model.

When you change an MCP tool's arguments

The registry records a schema pin: a hash of the tool's input definition. A mismatch means the caller's expected interface differs from the server's. Review the intended change, regenerate the pins, and rerun the affected tests:

& $Python -m ai_agent_lib_cli registry pin directory
& $Python -m pytest
& $Python -m ai_agent_lib_cli check

For CSV, REST, and Redshift examples, continue with the data tutorial and the CLI reference.

6. Choose the right test

Start with the smallest test that can reveal the mistake. Add a wider test when behavior depends on components working together.

TestQuestion it answersExample
Function testDoes this piece of business logic work?Does farewell trim whitespace?
Graph with FakesDo the graph and tool calls work together?Does a tool result reach the next model call?
Policy sampleDo the actual rules allow and deny the right requests?Can helper call farewell, while an unlisted application cannot?
As-configured testDo local configuration, registrations, and adapters fit together?Generated tests use local files and replace the model with scripted replies.
HTTP or MCP testDoes the service handle requests and failures correctly?An invalid request is rejected; an unavailable dependency keeps readiness false.
Live integration testDoes an external service behave as expected?A separately selected test calls a real cloud or database service.
Model evaluationDoes a real model produce useful answers?Run a fixed set of questions and score its responses.

The generated default test suite uses local substitutes and blocks connections to external hosts. Loopback remains available for local tests and Python's event loop. Live integration tests and evaluations are opt-in. Do not enable networking just to make a unit test pass; first check whether it should use a fake.

& $Python -m pytest agents/helper/tests/test_farewell.py
& $Python -m pytest
& $Python -m ai_agent_lib_cli check

check is the pre-commit routine: lint, format checking, type checking, tests, and policy samples. Lint catches suspicious code patterns; type checking catches inconsistent inputs and return types without running the application. CI (continuous integration) repeats these checks when code is submitted.

7. Troubleshoot a problem

First read the earliest failure. Expected library errors include the expected value, the actual value, and a suggested fix. Change one cause at a time, then rerun the smallest failing command.

What you seeWhat to check next
No module named helper or a missing packageUse the Python executable from setup. Run agentlib install through that interpreter after adding a service or dependency.
pip cannot find a dependencyCheck the configured package index, proxy, and supported Python version. For an offline machine, ask for compatible wheels. pip still needs prebuilt wheels for dependencies with native code if compilation is unavailable.
A setting appears to be ignoredRun config explain helper. A process environment variable may be overriding .env. Restart after editing configuration.
ConfigurationErrorCheck spelling and JSON syntax with config options, then run doctor helper. Unknown options are rejected.
PolicyDeniedRead the reason code. Compare the caller, application, action, and resource with the intended rule. Add a policy sample before changing permissions.
The answer starts with fake:This is expected for the default model. Use a scripted test for tool behavior, or configure a real model.
Connection refused after linking MCPStart the registered MCP server and check its configured address and port.
/healthz works, but /readyz returns 503The listener is alive, but startup or graph/MCP preparation is incomplete. Read startup logs and check dependencies.
A tool schema pin does not matchCompare the server's tool arguments with the registry. Update pins only after reviewing the interface change.
BudgetExceededLook for a repeated model/tool loop or an oversized request. Reduce the work or deliberately adjust limits; repeating the same request may exhaust the budget again.

When reporting a bug, include the command, Python version, request ID, exception type, and a minimal reproducer. Remove credentials and sensitive data. Keep the full traceback: unexpected Python errors and lifecycle error groups are not necessarily subclasses of AgentLibError.

When you need more

The remaining sections explain extension points and deployment concerns. You can return to them as your application grows; they are not prerequisites for the local tutorial.

Architecture and dependencies

The design separates what a service must do from how it does it. A contract, also called a port, describes the methods a service provides. An adapter implements that contract. This keeps cloud SDK details out of business functions and makes those functions easier to test.

Your applicationTools, graph steps, query definitions, and application rules.
ai-agent-lib-coreContracts, configuration, service composition, call checks, local adapters, and optional framework integrations.
ai-agent-lib-awsAWS adapters and their optional dependencies.
ai-agent-lib-cliProject generation, diagnostics, installation, checks, and deployment generation.

Dependency injection in ordinary Python

Dependency injection means giving a component the services it needs instead of having it create them internally. The generated build_graph(services) receives a container. Tests supply a container with fakes; the running application supplies one built from configuration.

Keep the tool's business logic in functions or small classes with clear inputs. Use the container at the place where components are assembled. Avoid looking up a global container from arbitrary functions or importing a cloud client into code that only needs a model or a query interface.

Adding your own adapter

  1. Choose the contract from ai_agent_lib_core.contracts and implement its methods.
  2. Create a factory that accepts a BuildContext. Declare required singleton dependencies in ServiceProviders.register(..., dependencies=...).
  3. Use a typed descriptor, such as AUDIT or SECRETS, when registering or resolving a port. ServicePort[T] preserves the expected Python type; existing string registrations remain supported.
  4. Define an options model for configuration, and declare any deployment access the adapter requires. Test it with the shipped contract suite as well as its own tests.

The container checks dependencies before constructing adapters. Runtime member checks catch missing methods; contract tests check their behavior. See the registration example for the factory and typed registration syntax.

Who starts and closes resources?

The container owns the adapters it creates and closes dependents before their dependencies. Each adapter has an isolated task for construction and teardown. Cleanup is awaited during cancellation; failures are reported. A factory must clean up resources it acquired before its own startup failed.

Shared resources belong to one container through BuildResources, not to the provider registry. An explicitly injected, caller-owned AWS session remains the caller's responsibility. See the ownership decision before writing adapters that own connections or background tasks.

What happens during a call

A pipeline is a sequence of checks around an operation. Calling a model obtained from services.model(), or a tool wrapped by services.tools(), runs through the library's pipeline.

Depending on the operation, it validates caller and registration information, asks policy for permission, checks content, applies limits, invokes the adapter, checks the result, and records the outcome. A denial prevents the protected operation from running. Tools exposed through MCP also use registrations and schema pins.

Use the container's compile_kwargs() when compiling a graph and invocation(context) when invoking it, as the generated code does. These connect checkpoint state and request context to the graph. A checkpoint stores conversation state so later calls can continue it.

EAP_LIMITS controls timeouts, retries, and request budgets. Read-only tools can retry transient failures; write operations should not be assumed safe to retry. Budgets are process-local and tied to live request contexts. Token accounting uses reported usage after calls, so it is not a reservation system or a distributed billing limit.

Return structured output

If another program needs to read the answer, define a schema instead of parsing free-form text. A Pydantic model specifies fields and their types; the library validates the returned value.

This complete function can live in an application module. Its caller supplies an open container, a request context, and the text to classify:

from typing import Literal

from ai_agent_lib_core import RequestContext, ServiceContainer
from ai_agent_lib_core.pipeline import bind_request_context
from langchain_core.messages import HumanMessage, SystemMessage
from pydantic import BaseModel


class Triage(BaseModel):
    category: Literal["billing", "technical", "other"]
    urgent: bool


async def classify(
    services: ServiceContainer, context: RequestContext, text: str
) -> Triage:
    model = services.model().with_structured_output(Triage)
    with bind_request_context(context):
        result: Triage = await model.ainvoke(
            [SystemMessage("Classify the support request."), HumanMessage(text)]
        )
    return result

The adapter must support structured output; unsupported operations are rejected. Invalid output raises ValidationFailed. In a fake-model test, script the result with structured_reply(Triage(category="billing", urgent=False)) from ai_agent_lib_core.testing. Test invalid replies too, so the application handles them deliberately.

Understand logs, audit records, and traces

SignalUse it to answerWhere to start
LogWhat error or event happened in this process?The generated HTTP service writes JSON lines to its output.
Audit recordWho attempted which action, and was it allowed?Locally, check the service's .agentlib/audit.jsonl.
TraceWhich calls made up this request, and where was time spent?Enable OpenTelemetry and inspect the request's connected spans.
MetricHow often does something happen, or how slow is it overall?Inspect counts and durations in your telemetry backend.

A span records one operation within a trace. Model, tool, query, and HTTP operations have spans, and MCP calls propagate trace context. Use the request ID to connect an observed failure with logs and audit records.

Generated HTTP services already initialize logging and telemetry. To export telemetry, install the core otel extra and configure a reachable collector:

EAP_TELEMETRY=opentelemetry
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318

This example assumes a collector listening locally; it does not start one. A collector receives and forwards telemetry to your team's backend. Leave telemetry disabled for the beginner tutorial if you do not have one.

The library's standard events record metadata rather than prompt and response bodies. Your own logging can still expose sensitive data. Review it before enabling a shared log destination, and never log credentials.

Evaluate answers from a real model

A scripted unit test proves the program follows a known sequence. An evaluation asks whether a real model chooses useful actions and produces acceptable answers for a set of examples. Keep both: they catch different problems.

  1. Configure a real model and its credentials for the agent.
  2. Review agents/helper/evals/cases.jsonl and the generated test_helper_eval.py. Each JSONL line is a separate example.
  3. Start required MCP services, if the evaluation uses them.
  4. Run the evaluation explicitly:
& $Python -m ai_agent_lib_cli eval helper

This selects the tests marked eval, which the normal test run excludes. A fake model causes the generated real-model evaluation to skip. Real evaluations use network access and can incur model charges; a fixed dataset does not make them network-free.

The evaluation package offers exact-match and model-judged scorers. Choose criteria that reflect the task, inspect individual failures, and avoid treating one aggregate score as proof that every response is correct. Continuous scoring of production traffic needs application-owned processing; the library does not deploy that worker for you.

Prepare the service for shared use

The local profile is for development. Before other people use the service, work with your platform team on these configuration and application responsibilities:

  • Identify callers and services. Configure the intended token issuer and audience. Give each agent and MCP server its own application identity. Use configured token exchange when an agent acts for a user at another service.
  • Grant specific actions. Name applications and resources in rules. Add denial samples as well as success samples. Keep data classifications and any row limits or column masking close to the named query.
  • Validate inputs and treat results as data. Keep tool-result framing enabled and configure appropriate guardrails. A model's suggestion does not replace authorization or business validation.
  • Keep secrets out of source and images. Use the configured secret provider and secret names. Keep local .env, logs, and state files out of commits and build inputs.
  • Review remote connections. Use HTTPS and the intended certificate trust. Keep schema pins current through reviewed changes.
  • Set the real deployment environment. Do not leave EAP_DEPLOYMENT_ENV=local in a shared deployment. Non-local startup rejects development-only adapters.

If your deployment uses OPA (Open Policy Agent, an external policy engine), run agentlib policy test --opa on a machine with OPA available to check that its decisions agree with the local samples. OPA is not required for the local walkthrough.

Deploy on AWS when the application is ready

Deployment is a separate workflow. Local development needs Python and pip; building container images and applying infrastructure needs a suitable build machine or CI environment with the relevant tools and credentials.

agentlib deploy generates files for AWS ECS Fargate, a managed container runtime. It does not provision AWS resources or apply Terraform for you.

  1. Run the command once to create agents/helper/deploy.env:
& $Python -m ai_agent_lib_cli deploy helper

Edit that file with your platform's non-local settings. Use secret references, not secret values. Add the required adapter extras to the service's dependencies.

Then inspect the plan and generate the deployment files:

& $Python -m ai_agent_lib_cli deploy helper --plan
& $Python -m ai_agent_lib_cli deploy helper

The plan explains adapter dependencies, AWS permissions, sidecars (supporting containers), and warnings. Review deploy/helper/README.md for the generated build and Terraform steps, including the hash-checked requirements.lock.

The generated Dockerfile-specific allowlist limits the image build inputs to the selected service and required shared files. It excludes environment files, caches, audit logs, and local state. Review custom Dockerfiles when upgrading: some deployment files are user-owned and are not automatically replaced.

The platform must supply the cluster, networking, image repositories, secrets, and the external resources the adapters use. Load balancers should check /readyz: the listener opens before startup completes, and readiness waits for validation and graph/MCP preparation. /healthz only reports liveness.

Example permissions derived from adapter settings

IAM is AWS's permission system. Adapters declare the actions and resources they need; the generator turns those declarations into a plan. This example combines the starting agent deployment settings with a Redshift data source. Your plan will depend on your own settings.

Review any check: notes where a resource could not be narrowed from configuration. Custom adapters should declare access explicitly as well.

Know which features are available

The specification describes the target design. The release scope records current behavior, tests, and deliberate differences from that target. Use it when planning a feature.

Current features include configuration and adapters, governed model/tool calls, identity and policy integrations, named queries, conversation checkpoints, HTTP and MCP serving, local test helpers, and deployment generation.

Do not assume the library provides human approval workflows, idempotency guarantees, long-term memory, distributed spending limits, or token-by-token streaming. The HTTP streaming endpoint currently sends graph steps. The architecture decision records explain the design choices.

Keep code and its documentation consistent

The code uses small interfaces and constructor injection: a component receives the objects it needs instead of looking up global services. Prefer an existing interface when it describes the job. Add a new abstraction when it separates a responsibility or makes a dependency replaceable in tests, rather than simply adding another class.

Name things by their role

  • Use snake_case for modules, functions, methods, and variables; PascalCase for classes; and UPPER_SNAKE_CASE for constants. Prefix internal helpers with _. Keep established public names stable, including exceptions such as PolicyDenied.
  • A port describes a role, such as AuditSink. An adapter implements it. A provider name selects a factory in configuration. ProviderSpec is the factory definition; the container holds the live instance.
  • Use established suffixes when they help: Options for validated adapter settings, Interceptor for a pipeline stage, Bindings for integration assembly, and Answers for CLI generation inputs. Name functions for the action they perform.
  • Keep external and Python names distinct. The service claims-mcp uses the package claims_mcp and defaults to the registry ID claims. A model alias such as default is separate from a provider name such as anthropic and the provider's model ID.
  • Use request_id for correlation, thread_id for a conversation, and invocation_id for one invocation's budget. Do not reuse one identifier merely because all three are strings.

Document the contract and the reason

Start a module docstring with its responsibility and boundaries. Start a class docstring with its role, and document constructor arguments there. For a public function, explain what the caller must provide and can rely on. Use the existing Google-style Args:, Returns:, Raises:, and Attributes: sections when they add useful detail; a clear one-line docstring is enough for a simple accessor.

For resources, explain who creates and closes them. For async work, explain cancellation, cleanup, and side effects. For example, entering a ServiceContainer builds adapters; validate() is an explicit readiness step. A timeout does not prove that a remote write was undone, and token usage counted after a response is not a reservation made before the call.

Use comments for decisions that the code alone does not explain, such as why cleanup must run in the task that created a resource. Avoid comments that merely restate an assignment. Keep the full caller contract at the public entry point; an internal collaborator can refer to it and explain only its own responsibility. When a behavior changes, update its docstring, regression test, generated template, and example together where applicable.

Ruff checks naming and Google-style docstrings, mypy checks types, and Import-linter checks dependencies. These tools cannot prove that a comment is true: review promises such as “always,” “never,” “atomic,” and “thread-safe” against failure paths as well as the successful path. Keep executable examples complete, and distinguish tests using permissive fakes from tests of real policy and registry configuration.
