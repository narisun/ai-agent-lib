Introduction: principles and the core idea

An agent has a business job, such as answering a question about an account. It also needs to know who is calling, check permissions, protect data, record actions, and handle failures. These supporting responsibilities are called cross-cutting concerns because many different features need them.

ai-agent-lib gives each responsibility a clear home: your application defines the workflow and business logic, shared pipelines apply checks around calls, and adapters connect to models and other services. This structure centralizes common rules and lets tests replace external dependencies with controlled implementations. The specification also calls this mechanism an interceptor chain, and the code names one stage an Interceptor; this guide says pipeline for the same fixed-order sequence, described in What happens during a call.

Consider a tool that looks up an account balance. Its business job is to return the balance. Before calling it, the application needs a caller identity and a permission decision; afterwards, it needs a record of what happened. Keeping these responsibilities separate lets you change how permissions are checked without rewriting the balance calculation.

Keep these three responsibilities in view as you read:

  • Your application owns the graph, prompts, and business functions.
  • The library applies shared checks and manages service resources.
  • Providers supply implementations suited to your environment, connecting to local files or external services.

Start with familiar design principles

The design builds on principles used in web services and business applications:

PrincipleWhat it meansHow this library applies it

Use classes to own state, resources, or replaceable dependencies. Use functions for calculations and tools with explicit inputs and outputs. In the tutorial, a greeting tool is a function; the container is an object that owns service resources. Both fit this design.

Define interfaces and inject dependencies

A contract, also called a port, defines the operations a consumer may use and what they promise. An adapter implements those operations. A provider registration gives an adapter a configuration name and a factory that builds it.

The library defines interfaces with typing.Protocol. A class implements a protocol by providing compatible methods; inheritance is optional. Implementations must also preserve the contract's behavior. For example, Clock.now() returns a timezone-aware UTC value.

Example: inject a clock for a repeatable test

The application class Expiry receives a Clock through its constructor. The test supplies the library's FrozenClock to control time. After completing setup, you can save this as tests/test_expiry.py in the tutorial workspace and run it with pytest.

from datetime import UTC, datetime, timedelta

from ai_agent_lib_core.contracts import Clock
from ai_agent_lib_core.testing import FrozenClock


class Expiry:
    """Calculate expiry times using the clock supplied by the caller."""

    def __init__(self, clock: Clock) -> None:
        self._clock = clock

    def after(self, seconds: int) -> datetime:
        return self._clock.now() + timedelta(seconds=seconds)


def test_expiry_uses_the_supplied_clock() -> None:
    clock = FrozenClock(datetime(2026, 1, 1, tzinfo=UTC))
    expiry = Expiry(clock)

    assert expiry.after(60) == datetime(2026, 1, 1, 0, 1, tzinfo=UTC)
    clock.advance(30)
    assert expiry.after(60) == datetime(2026, 1, 1, 0, 1, 30, tzinfo=UTC)

Running code can supply SystemClock from ai_agent_lib_core.adapters to the same constructor. The calculation stays the same; the test controls its input time through the clock interface.

Dependency inversion is the rule about depending on a contract. Dependency injection passes the selected implementation to a consumer. Explicit dependencies make the component easy to test; a container automates the assembly of larger groups of components.

The HTTP layer has a worked example of a port and its adapters. To keep turns on one conversation thread in order, agent_app asks a ThreadAdmission port for ownership of the thread. The library supplies an in-memory adapter; a deployment with several worker processes injects its own. Keep conversation turns in order shows the port, the default adapter, and what a replacement must preserve.

Connect the parts in one place

The place that builds and connects an application's components is often called its composition root. Here the entry point loads configuration and opens a ServiceContainer. The container uses ServiceProviders to find the registered factories, builds their dependencies in order, and owns their lifetime.

Configuration→Registered factories →Container→ Adapters + pipelines→Graph and tools
Names for the patterns used in this assembly

This combines familiar patterns: ports and adapters separate contracts from integrations; factories build configured objects; decorator-style wrappers add checks around an operation; and the container is a facade offering a small set of assembly methods.

Use the container when assembling a graph or service. Pass each business component the specific interfaces it needs through function or constructor parameters. That keeps its dependencies visible to readers and tests.

LangGraph owns the workflow; the library supplies governed operations

Your graph uses LangGraph state, nodes, edges, and tool routing. Your application owns prompts and business rules. ai-agent-lib supplies model, tool, and data operations with shared enforcement around them. A governed operation means a call that goes through those checks.

At the integration boundaryWhat it connects
services.model()A LangChain-compatible model wrapper applies the model pipeline before and after the selected provider's call.
services.tools(...)Local Python functions become tools with permission checks, limits, and audit recording.
await services.mcp_tools(...)Registered remote tools become graph tools through the MCP integration. The MCP server also enforces its own controls.
services.data_source(name)A governed data source applies policy and data obligations, such as masking, around queries.
services.compile_kwargs()The selected checkpoint backend is connected when the graph is compiled.
services.invocation(context)Caller and conversation information are connected when the graph runs.

For example, a tool call goes from the graph to the governed tool, through its pipeline, to the function, and back with a recorded outcome. The policy stage asks a PolicyDecisionPoint for a decision. That interface can be implemented by local rules or an OPA policy service. The audit stage similarly writes through AuditSink, allowing the storage adapter to be replaced.

How the source code keeps the LangGraph boundary

Framework-neutral contracts and pipelines live below integrations/langgraph. That integration translates them to framework types. Model and checkpoint ports expose native objects through a neutral boundary; the integration checks their types and capabilities. This keeps LangGraph details out of the shared contracts, while the application graph itself remains LangGraph code.

Declare the service; run_agent runs it

A service need not write its own composition root. The generated agents, the reference accounts-agent, and rmprep declare what is theirs in one AgentService and pass it to run_agent. This is the generated helper agent's service.py, trimmed to the essentials; the generated file adds streaming, the outcome journal, main(argv) and the __main__ guard:

from typing import Any

from ai_agent_lib_core import RequestContext, ServiceContainer
from ai_agent_lib_core.integrations.http import AgentService, run_agent

from helper.graph import APPLICATION, answer, build_graph, registered_mcp_tools
from helper.settings import ENV_FILE


async def _build_graph(services: ServiceContainer) -> Any:
    return build_graph(services, await registered_mcp_tools(services))


async def _respond(
    graph: Any, services: ServiceContainer, context: RequestContext, question: str
) -> dict[str, Any]:
    return {"answer": await answer(graph, services, context, question)}


SERVICE = AgentService(
    application=APPLICATION,
    build_graph=_build_graph,
    respond=_respond,
    env_file=ENV_FILE,
)


def main() -> int:
    return run_agent(SERVICE)

python -m ai_agent_lib_cli run helper starts the module that calls main(), which serves the agent until the platform stops it. The two sides of that call have separate jobs:

OwnerResponsibility
Your service (AgentService)The application name; the graph, built once after the container is validated and before the service reports ready; how respond turns a question into an answer; how the question is read from the request's input, by default its non-empty question string; and its own .env file.
run_agentLoading configuration, logging, telemetry, agent tracing when Phoenix is enabled, opening and validating the container, readiness, serving HTTP with --host and --port, and closing everything in order when the process stops.

This is the composition root as one function. A change to how every service starts, traces, or stops lands once in run_agent, not in each agent. Inside build_graph and respond the graph should reach models, tools, and data through the operations in the integration-boundary table above; the runner supplies the services container they use. A service with unusual needs can still compose by hand with agent_app and serve.

Route external calls through the governed interfaces.

A graph node that constructs an SDK client and calls it directly bypasses these wrappers. Keep external operations behind the provided interfaces. Test provider changes for supported capabilities, response quality, latency, and data behavior.

Choose implementations for the environment

A profile supplies default adapter choices. Each concern can be configured independently using its installed adapter and required options. These defaults come directly from the library's configuration definitions:

Local adapters use a configured development identity, files, and a SQLite database. The AWS defaults use signed JWT tokens, an OPA policy service, PostgreSQL, and AWS services such as Secrets Manager, Firehose, S3, and Bedrock. The patterns guardrail checks configured text patterns. The tutorial selects fake, an in-process model that returns predictable responses. See the adapter options for each provider's setup.

Named data sources are selected separately through DataSource: examples include duckdb_csv for local CSV data, redshift_data for Redshift, and rest for HTTP APIs. Telemetry, clocks, and ID generators have their own configuration or injection points outside these profiles. Tests inject a recording telemetry implementation, frozen time, and predictable IDs.

AC2_PROFILE chooses defaults; per-concern settings such as AC2_AUDIT_PROVIDER override them. AC2_DEPLOYMENT_ENV describes where the process runs and controls checks such as rejecting local-only adapters outside local development. To use the AWS profile, install its packages and supply the required endpoints, credentials, permissions, and storage. See configuration for the steps.

Make reliability and extension part of the contract

A replacement must preserve the interface's behavior. For example, an audit sink must store a record durably or report a storage failure. Typed ports check required members, static checks catch type mistakes, and contract tests exercise behavior. Integration tests verify the connection to the external service.

  • Test business behavior in isolation. Fakes supplies a test container with scripted model replies and inspectable audit records. Tests run the same graph and pipelines with controlled collaborators.
  • Test actual rules separately. Fake policy and guardrails allow by default. Configuration tests and policy samples must also exercise the service's real rules, registry, denials, and data restrictions.
  • Validate assembly and ownership. Declared dependencies are checked before construction. The container closes owned adapters in reverse dependency order, and readiness waits for validation and preparation.
  • Extend at the right boundary. Implement a port, register its factory and dependencies, describe its options, and run its contract and integration tests. The extension walkthrough explains the registration and cleanup responsibilities, and release scope has a short ServiceProviders.register example.

Key types and terms

Graph
A set of steps and the connections between them. LangGraph runs these steps. In this example, the graph asks the model, runs tools if requested, and asks the model again.
State
The information carried between graph steps. Here it includes the conversation's messages.
ServiceContainer
The object that creates and owns the configured services. Your code receives it as services and asks it for a model, tools, or a data source.
RequestContext
Information about one request: who is calling, the application, the request ID, and the conversation ID. A Principal represents the caller; a tenant identifies their organization or account group.
Policy
Rules deciding whether that caller and application may perform an action on a resource. For example, may helper call greet?
Adapter and provider
An adapter implements a service, such as a fake model or an AWS model. Configuration selects it by a registered provider name. This lets application code use the same interface with different implementations.
MCP
Model Context Protocol: a standard way to expose tools from a separate server. Use it to share tools across agents or service boundaries.

Follow one request

Question→Entry point →RequestContext→ Graph→Model / tools →Answer

The entry point handles input and authentication. The graph decides which step runs next. The library applies policy, content checks, limits, and audit recording around model and tool calls. The tool function itself can stay small.

The graph and service entry points use async/await for I/O. async with ServiceContainer(...) starts the configured adapters and closes them when the block ends. Tools such as greet are synchronous functions.

Step D: test the graph's tool call

Create agents/helper/tests/test_farewell_graph.py:

from ai_agent_lib_core import Principal, RequestContext
from ai_agent_lib_core.pipeline import frame_untrusted
from ai_agent_lib_core.testing import FakeChatModelProvider, Fakes, calls_tool

from helper import APPLICATION, ask


async def test_agent_uses_farewell() -> None:
    fakes = Fakes(
        model=FakeChatModelProvider([calls_tool("farewell", name="Ada"), "I said goodbye to Ada."])
    )
    context = RequestContext(
        principal=Principal(subject="learner", tenant="tutorial"),
        application=APPLICATION,
        request_id="farewell-test",
        thread_id="conversation-1",
    )

    async with fakes.container() as services:
        reply = await ask(services, context, "Say goodbye to Ada.")

    assert reply == "I said goodbye to Ada."

What does a model trace contain?

Event or fieldWhat to inspect
model.requestmessages in their sent order, normalized tool definitions, tool-binding options, and per-call options such as stop sequences.
model.responseThe returned AI message: content, tool calls and arguments, message ID, usage, and metadata supplied by the provider.
model.errorThe exception type from the provider attempt. Error bodies are omitted because they may contain credentials or unrelated request data.
request_id and thread_idOne request and the conversation it belongs to. Tenant, subject, and application identify its scope.
call_id and attemptMatch a request with its response or error. A retry keeps the call ID and increments the attempt; another graph model step gets a new call ID.

The trace records complete LangChain message objects at the provider boundary, before output guardrails or structured-output validation. A recorded response can therefore still be rejected by the pipeline; check audit records for the final outcome. Tool definitions use a common function-schema format. Provider SDKs may transform messages and schemas into a different HTTP body. Unrecognized non-JSON objects are represented by type. This trace does not intercept SDK HTTP traffic or expose a model's private internal reasoning.

Why is the trace empty or incomplete?

Run "%PYTHON%" -m ai_agent_lib_cli config explain helper to verify the path and its source. Restart after changing settings. Calls must use services.model() to be captured. A policy or input-check denial can stop a request before it reaches the provider, so look at the audit record too.

A request followed by model.error means the provider attempt failed or was cancelled. A process stopped abruptly can leave a request without a response event. model_trace.disabled in operational output means serialization or writing failed; check the destination and available disk space, then restart after fixing it. Trace failures preserve the model's normal outcome. Trace files are diagnostic captures, not durable audit records.

Implement and register the adapter

  1. Choose the contract from ai_agent_lib_core.contracts and implement its methods.
  2. Create a factory that accepts a BuildContext. Declare required singleton dependencies in ServiceProviders.register(..., dependencies=...).
  3. Use a typed descriptor, such as AUDIT or SECRETS, when registering or resolving a port. ServicePort[T] preserves the expected Python type through registration and resolution.
  4. Define an options model for configuration, and declare any deployment access the adapter requires. Test it with the shipped contract suite as well as its own tests.

The container checks dependencies before constructing adapters. Runtime member checks catch missing methods; contract tests check their behavior. See the registration example for the factory and typed registration syntax.

Who starts and closes resources?

The container owns the adapters it creates and closes dependents before their dependencies. Each adapter has an isolated task for construction and teardown. Cleanup is awaited during cancellation; failures are reported. A factory must clean up resources it acquired before its own startup failed.

Use BuildResources to share resources within one container. The caller remains responsible for closing an explicitly injected, caller-owned AWS session. See the ownership decision before writing adapters that own connections or background tasks.

What happens during a call

A pipeline is a sequence of checks around an operation. Calling a model obtained from services.model(), or a tool wrapped by services.tools(), runs through the library's pipeline.

Before execution, the applicable identity, registry, policy, and input checks must pass. The pipeline applies limits, invokes the operation, checks its result, and records the outcome. MCP tools also use registry entries and schema pins.

Use the container's compile_kwargs() when compiling a graph and invocation(context) when invoking it, as the generated code does. These connect checkpoint state and request context to the graph. A checkpoint stores conversation state so later calls can continue it.

AC2_LIMITS controls timeouts, retries, and request budgets. Read-only tools can retry transient failures. For write operations, design retry behavior around the possibility that the remote action completed before a timeout.

Audit or output-validation failures can happen after an external action succeeds; they do not undo that action. Budgets apply within one process and account for reported token usage after calls. Use the release scope when designing recovery or spending controls across services.

Return structured output

Define a response schema when another program consumes the answer. A Pydantic model specifies fields and their types; the library validates the returned value.

This complete function can live in an application module. Its caller supplies an open container, a request context, and the text to classify:

from typing import Literal

from ai_agent_lib_core import RequestContext, ServiceContainer
from ai_agent_lib_core.pipeline import bind_request_context
from langchain_core.messages import HumanMessage, SystemMessage
from pydantic import BaseModel


class Triage(BaseModel):
    category: Literal["billing", "technical", "other"]
    urgent: bool


async def classify(
    services: ServiceContainer, context: RequestContext, text: str
) -> Triage:
    model = services.model().with_structured_output(Triage)
    with bind_request_context(context):
        result: Triage = await model.ainvoke(
            [SystemMessage("Classify the support request."), HumanMessage(text)]
        )
    return result

The adapter must support structured output; unsupported operations are rejected. Invalid output raises ValidationFailed. In a fake-model test, script the result with structured_reply(Triage(category="billing", urgent=False)) from ai_agent_lib_core.testing. Test invalid replies too, so the application handles them deliberately.

Evaluate answers from a real model

A scripted unit test proves the program follows a known sequence. An evaluation asks whether a real model chooses useful actions and produces acceptable answers for a set of examples. Keep both: they catch different problems.

  1. Configure a real model and its credentials for the agent.
  2. Review agents/helper/evals/cases.jsonl and the generated test_helper_eval.py. Each JSONL line is a separate example.
  3. Start required MCP services, if the evaluation uses them.
  4. Run the evaluation explicitly:
"%PYTHON%" -m ai_agent_lib_cli eval helper

This command selects tests marked eval. They require network access to the configured model and use your account's quota and billing. The generated evaluation skips when the selected model is fake. Each run writes agents/helper/.agentcraft2/eval-report.json, with the mean for each metric and every case's score. The .agentcraft2 folder is excluded from version control, so open the file to inspect individual failures alongside the aggregate score.

Protect a baseline

When the scores are ones you want to protect, accept them:

"%PYTHON%" -m ai_agent_lib_cli eval helper --accept

--accept runs the evaluation itself and, if it passes, saves the report as agents/helper/evals/baseline.json. Commit that file with cases.jsonl: both hold synthetic cases and aggregate scores, not conversation content. From then on every run is also a regression gate. It fails when any metric's mean falls more than 0.05 below the baseline, even if the score still clears the absolute bar, and it names the regressed metrics and the cases whose own score dropped. Run --accept again when a drop is intended, such as a new model or a rewritten prompt; that run skips only the baseline comparison, so it must still pass the absolute bar. Accept a new baseline after you add or edit cases on purpose; the gate does not notice that the dataset changed.

Judges

Scorers range from exact-match checks to model-judged ones. Use a judge for qualities that code cannot match, such as tone or faithfulness to evidence, and build it from the judge model alias rather than a fixed model ID. A judge is a model call that can be wrong, so run calibrate to compare it with answers a person has already graded before you let its score gate anything.

Online evaluation

Ordinary scorers such as judges also run over what your service has already answered. Agent Lab records thumbs up or down beneath each accepted answer in feedback.jsonl. export_interactions turns saved conversations, joined with that feedback, into interaction records. sampled then picks a reproducible slice, and score_interactions scores it with ordinary scorers into an ordinary report; it does not call the agent again. Exporting is a Python entry point, not yet a CLI command. Feedback logs and exports hold real conversation content, so keep them in private .agentcraft2/ state and never commit them.

The evals guide covers the dataset and report formats, the generated test, judges and calibration, the export and scoring scripts, and privacy in full.

Prepare the service for shared use

The local profile is for development. Before other people use the service, work with your platform team on these configuration and application responsibilities:

  • Identify callers and services. Configure the intended token issuer and audience. Give each agent and MCP server its own application identity. Use configured token exchange when an agent acts for a user at another service.
  • Grant specific actions. Name applications and resources in rules. Add denial samples as well as success samples. Keep data classifications and any row limits or column masking close to the named query.
  • Validate inputs and treat results as data. Keep tool-result framing enabled and configure appropriate guardrails. Apply authorization and business validation before acting on a model's suggestion.
  • Keep secrets out of source and images. Use the configured secret provider and secret names. Keep local .env, logs, and state files out of commits and build inputs.
  • Review remote connections. Use HTTPS and the intended certificate trust. Keep schema pins current through reviewed changes.
  • Set the deployment environment. Configure AC2_DEPLOYMENT_ENV for the target environment. Non-local startup checks reject development-only adapters.

If your deployment uses OPA (Open Policy Agent, an external policy engine), run "%PYTHON%" -m ai_agent_lib_cli policy test --opa on a machine with OPA installed to verify its decisions against the policy samples.

Name things by their role

  • Use snake_case for modules, functions, methods, and variables; PascalCase for classes; and UPPER_SNAKE_CASE for constants. Prefix internal helpers with _. Keep established public names stable, including exceptions such as PolicyDenied.
  • A port describes a role, such as AuditSink. An adapter implements it. A provider name selects a factory in configuration. ProviderSpec is the factory definition; the container holds the live instance.
  • Use established suffixes when they help: Options for validated adapter settings, Interceptor for a pipeline stage, Bindings for integration assembly, and Answers for CLI generation inputs. Name functions for the action they perform.
  • Keep external and Python names distinct. The service claims-mcp uses the package claims_mcp and defaults to the registry ID claims. A model alias such as default is separate from a provider name such as anthropic and the provider's model ID.
  • Use request_id for correlation, thread_id for a conversation, and invocation_id for one invocation's budget. Keep these identifiers distinct in data models and logs.

How the settings fit the AWS design

Run agents and MCP servers as ECS Fargate services. The generated deployment runs OPA as a sidecar in each service's task; a separate OPA service is also possible through the policy URL. The future frontend signs users in with Microsoft Entra ID. Each backend verifies an access token issued for its API; an agent obtains a downstream MCP token using Entra's on-behalf-of flow. The local static identity supplies test subjects, tenants, and roles through configuration instead. See identity setup for API registrations, roles, scopes, and audiences.

  • Business data: MCP tools use named queries against the existing curated Redshift tables through the Redshift Data API. The upstream data lake remains outside this application.
  • Operational data: use managed PostgreSQL for checkpoints and the team's registry and role/resource mapping tables. The current postgres adapter implements checkpoints only. RDS for PostgreSQL and Aurora PostgreSQL support IAM database authentication; RDS Proxy with IAM is an optional connection-pooling layer. Registry tables need a new provider or a publishing job that produces the current S3 registry format. Mapping tables need an integration that supplies policy data, such as OPA data bundles. No environment variable creates these integrations. Keep their schemas and migrations separate from the library's checkpoint tables.
  • Logs in S3: the audit provider sends records to Firehose; configure an S3 destination on that stream. The generated Fargate template sends container logs to CloudWatch Logs. To archive agent, MCP, and OPA logs in S3, add a delivery route such as FireLens to Firehose. Diagnostic model traces need a collector that reads their file. S3 delivery for container logs and diagnostic files is additional infrastructure; the generated template does not configure it.
  • Files in S3: use S3 objects for durable documents, exports, and registry snapshots. File-path options still mean paths inside the container; setting them to s3://... does not add S3 access. Package static SQL and policy files in images, or arrange a download before startup. Use temporary task storage for scratch files. If an application needs a shared filesystem with file operations, EFS is a supported Fargate option; it requires a volume configuration. The library has no general filesystem provider or automatic S3 upload for application files.

Fargate CPU, memory, images, networking, task roles, databases, log delivery, S3 retention, and OPA bundle distribution are infrastructure settings. The deployment team configures them through the generated Terraform files and platform services; they are not additional AC2_ variables.
